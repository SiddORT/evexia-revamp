# EVEXIA Portal

EVEXIA Life Sciences portal with protected Admin and MR workspaces, a mock Doctor login screen, browser-local demonstration masters, and a FastAPI authentication/API service. Admin/MR authentication, Staff Management, Roles, Zone, Courier Partner, Storage Location, Designation, Headquarter, Product Category, Allergen, MR, Doctor, Patient, Vendor and Sales Target Masters use the backend; unrelated masters remain browser-local.

## Run & operate

- Doctor/Patient directory-only soft deletion uses additive `0028_directory_soft_delete`
  after accepted `0027_mr_designation_identity`. Nullable time/User metadata retains
  records and global uniqueness; deleted records are absent from live masters and
  choices. Saved Doctor references remain readable/unavailable and can be retained
  unchanged; Patient identity, status, assigned MR and private files are preserved.
  Readiness requires the migration; managed schema/API/frontend rollout needs
  separate approval and a coordinated backup. See the Doctor/Patient operations docs.

- Live MR designation uses required server UUID identity and derived readable names, not free text. Forward `0027_mr_designation_identity` follows the reduced designation cleanup; all historical labels must uniquely normalize to catalogue records or migration aborts. Managed rollout needs separate approval, backup and coordinated schema/API/frontend release; populated downgrade is refused. Local text stays unchanged. See `docs/mr-master.md`.

- The managed `artifacts/evexia-portal: web` workflow serves the portal preview.
- Loading presentation is request-driven: the HTML startup fallback and Admin access checks use the unchanged official logo; reporting tables use decorative cell skeletons with one status announcement. Local Master reads remain synchronous. Run `pnpm --filter @workspace/evexia-portal run test:loaders:browser` for loading, authenticated draft/session, and Activity Logs browser regressions.
- `pnpm --filter @workspace/evexia-portal run build` builds the web app.
- The managed `artifacts/api-server: API Server` workflow runs FastAPI directly with Python on `/api` (no Node.js or pnpm in the API artifact). The portal calls same-origin `/api/v1/auth` routes through its API proxy. API code and operational notes are in `artifacts/api-server/backend/README.md`. Database changes use Alembic migrations; do not create tables at startup.

## Stack and scope

- Shared Allergen Master is protected singleton-only (no assignable staff Allergen permissions). `mix=true` means Mix; `false` means No Mix, catalogue metadata only. It uses shared category/location references, exact optional decimal strings, versioned soft deletion and bounded CSV/XLSX review/confirm/filtered exports with durable acceptance. No HSN in the current catalogue; explicit legacy CSV HSN is ignored. Migration `0022_allergen_catalogue` is empty and requires operator approval for managed rollout. The original local allergen/category/location and procurement datasets stay separate and untouched. See `docs/allergen-master.md`.

- Product Category Master is protected singleton-only shared persistence with exact `NUMERIC(18,6)` prices, server price/status/search filters, versioned soft deletion and bounded CSV/XLSX review/confirm/downloads. Migration `0018_product_categories` starts empty after Headquarter. The legacy browser-local allergen dataset and procurement retain separate untouched local category IDs. See `docs/product-category-master.md`; managed migration requires separate approval.

- Headquarter Master is protected singleton-only shared persistence. Migration `0017_headquarters` creates an empty catalogue; names are live-unique, codes are editable HQ-name abbreviations (not geographic codes), mutations are versioned and deletion retains audit evidence. CSV/XLSX transfer supports legacy/current schemas, 2 MiB/1,000-row imports and 5,000-match exports with mandatory download acceptance. Local records/drafts remain untouched and unused. See `docs/headquarter-master.md`.

- React with JavaScript/JSX, Vite, Wouter, and CSS. Keep the web artifact free of TypeScript files.
- Routes: `/` (portal selection); `/admin/login` (backend-authenticated workspace login); `/mr` (server-authenticated MR workspace); `/doctor` (mock login); `/admin` and `/admin/*` (protected workspace).
- Admin routes require a verified backend session. The protected singleton has `admin.access`; explicitly enabled staff have only `workspace.access` and assigned Zone grants, with unrelated routes denied before mounting. The browser guard is not a substitute for server authorization. Sign Out revokes the server refresh session when available and clears the in-memory access token.
- The new backend is a separate foundation, not a replacement for existing browser-local master records. Do not silently migrate or overwrite those records.
- Doctor Master uses server records with MRProfile-linked IDs and derived MR Zones. Explicit staff Doctor grants permit only corresponding master actions; MR's associated-doctor viewer returns minimal bounded choices under MR grants. Migration `0019_doctor_directory` creates an empty table. Versioned/atomic actions, consuming-action PIN filling and full-field CSV/XLSX transfers never migrate local records or expose a payment ledger/login. Legacy opening-balance and demo-payment services remain unused local datasets. See `docs/doctor-master.md` and `docs/zone-role-permissions.md`.
- Opening Balance Master uses shared authenticated persistence with signed exact `NUMERIC(15,2)` amounts, adjacent financial years, live Doctor/year uniqueness and versioned soft deletion. It is protected Super Admin-only and outside the eight-master staff catalogue; its minimal bounded Doctor picker does not grant general Doctor access. `0024_opening_balances` creates an empty catalogue after `0023_sales_targets`; reconcile concurrent migration ancestry before operator-approved rollout. CSV/XLSX imports are create-only, atomic and single-use reviewed; downloads require durable logs. No local balances, doctors or payment-preview data are migrated or edited automatically, and no ledger/contact fields are introduced. See `docs/opening-balance-master.md`.
- Patient Master uses the empty one-to-one Patient identity extension `0020_patient_directory`, with live Doctor→MR→Zone references, transactional owner/status/version synchronization, full-field date-only/phone-country persistence and action-specific CSV/XLSX transfers. Explicit staff Patient grants exclude private files/treatment/history. Local Patient consumers remain untouched; live dosage/history never uses demo treatment. Operator approval is required for managed migrations; see `docs/patient-master.md` and `docs/zone-role-permissions.md`.
- All future backend work must follow the supplied EVEXIA Engineering and Security Standards. EVEXIA is non-tenant: use explicit system Super Admin/MR identities and database ownership/assignment policies, never tenant abstractions or implicit elevation from legacy memberships or portal role labels. See `artifacts/api-server/backend/STORAGE_CONTRACT.md`.
- Backend API and persistence contract: see `artifacts/api-server/backend/README.md`; FastAPI OpenAPI is authoritative and shared TypeScript clients are generated offline from it. Production uploads cannot rely on the app filesystem: Replit published app files reset on restart/publish, so use explicitly configured durable object storage and operator-managed data backups. See the backend README's official Replit documentation references and recovery procedure.
- Admin and MR authenticate against FastAPI with explicit portal-bound account verification. Access tokens are memory-only; rotating refresh credentials use an HttpOnly cookie. Login credentials are never stored in browser storage. Doctor login remains mock-only.
- Super Admin profile > Sessions & Activity Logs (`/admin/activity-logs`) is read-only backend reporting. Counts are global registered backend accounts and distinct eligible session owners, not local records or presence. Histories use server filters and UTC dates; no private history is persisted in browser storage. See the backend README for scope and pagination semantics.
- Super Admin profile > Download Logs (`/admin/download-logs`) is a separate append-only, metadata-only initiation ledger starting at rollout. All file releases require durable acceptance; server preparation/issuance and browser-reported handoffs never claim disk completion. See `docs/download-logs.md` for coverage, retry keys, migration and verification.
- Both reporting tabs keep independent debounced searches, with search and CSV export in a responsive toolbar outside the tablist. Activity search is literal, case-insensitive and bounded to 100 characters, matches safe displayed metadata and explicit friendly labels, and uses identical server matching for pages and the existing 5,000-row export. Keep backend reporting label aliases aligned with the page's action/resource labels; portable CSVs still exclude references.
- Zone Master is shared FastAPI/PostgreSQL persistence. Its page shows only the current non-deleted directory, with no Current/Deleted view buttons or explanatory header paragraphs. The protected singleton retains current-record actions; explicitly enabled staff require assigned `zone.add`, `zone.edit`, `zone.delete`, `zone.export` or `zone.import` capabilities. Any grant permits list/detail; backend trash/restore remain singleton-only, without a recovery entry point on this page. No local migration or mirroring occurs. Demo assignments still use separate legacy browser-local zones. See `docs/zone-master.md`.
- Courier Partner Master is separate shared FastAPI/PostgreSQL persistence under system Super Admin `admin.access`. Old browser-local data remains untouched and unused; explicit CSV/XLSX review/confirm is create-only. Exports allow 5,000 matches; imports allow 2 MiB/1,000 rows. See `docs/courier-partner-master.md`.
- Storage Location Master is a separate shared name/address/status directory protected by system Super Admin `admin.access`. Explicit migration `0012_storage_locations` creates an empty table. CSV/XLSX review/confirm is create-only; imports allow 2 MiB/1,000 rows and filtered exports 5,000 records. The legacy browser-local allergen dataset and PO/PR retain separate location datasets and IDs without migration or mirroring. See `docs/storage-location-master.md`.
- Designation Master is separate protected Super Admin-only name/short-name/status persistence, never authorized by Zone staff grants. Versioned mutations, soft deletion, reduced three/seven-column CSV/XLSX transfers and explicit ten/fourteen-column legacy imports preserve server attribution. Staff choices load up to 100 active server UUIDs; independently hydrated saved references remain preservable. No local migration or payroll. Forward `0026_designation_target` after `0025_vendor_phone` permanently drops seven designation columns and adds the exact stored generated Sales Target annual sum; backup and coordinated operator-approved rollout are required. Populated designation downgrades are refused and cannot restore removed values. See `docs/designation-master.md` and `docs/sales-target-master.md`.
- Vendor Master is protected singleton-only shared persistence outside the eight-master staff catalogue. Explicit `0022_vendors` creates an empty catalogue; versioned CRUD/soft deletion, six-field search/status paging and authenticated CSV/XLSX transfers preserve phone country and server audits. Add/Edit remains a modal with shared PhoneInput. Legacy local Vendor/PO/receipt records and IDs remain untouched and separate. See `docs/vendor-master.md`; managed migration/deployment requires separate approval.
- Sales Target Master is protected singleton-only shared persistence outside the eight-master staff catalogue. `0023_sales_targets` follows `0022_allergen_catalogue` and starts empty. Shared server MR references derive zone/headquarter; quarterly rupees are exact decimal strings; financial end year must equal start year + 1. Status/year/zone/MR/name filters and summaries/export cover all matches. Versioned soft deletion and bounded create-only CSV/XLSX transfers retain server audit evidence and explicit seven-column legacy CSV compatibility. No automatic migration or fallback to local target/MR/Zone stores. See `docs/sales-target-master.md`; managed migration/deployment requires separate approval.
- Settings > Communication is a demo-only Email (SMTP/API/unconnected platform), SMS and WABA metadata preview. Use dummy values only. No provider is connected, verified or contacted. Password/key/token preview inputs are transient and never saved; endpoint metadata uses HTTPS without embedded credentials, query strings or fragments. Communication resets affect only its dedicated browser-local metadata, not other settings or master records.
- Staff Management requires protected system Super Admin `staff.manage`. Encrypted directory fields and dedicated key handling remain unchanged. Credentials are provisioned without plaintext User.email or a system role. Staff login is disabled by default; only an explicit version-checked access change enables it and assigns a custom role ID. Business role/designation labels grant nothing. Existing generated User ID/password are reused, never reset or redisplayed on enablement. Active status is also required; disable/inactivation revokes sessions. See `docs/staff-security.md`.
- Staff uses required catalogue `designation_id` and read-only `designationName`; unchanged inactive/deleted references remain retainable. Forward `0028_staff_designation_lifecycle` follows merged `0028_directory_soft_delete` after MR `0027` and requires complete reviewed historical mapping before removing text; read-only preflight and exact-label UUID overrides never create catalogue rows. Versioned soft deletion retains encrypted profiles, Users, status and relationships, revokes sessions and excludes tombstones from normal operations/authentication, not backup/rotation/history. Managed rollout requires separate approval, backups and coordinated schema/API/frontend; populated downgrade is refused. See `docs/staff-security.md`.
- Roles & Permissions requires protected system Super Admin `roles.manage`. Custom roles default to empty grants. Exactly eight masters have five assignable actions each: Headquarter, Zone, MR, Patient, Doctor, Product Category, Storage Location and Courier Partner. All/Clear select the catalogue, not broad administrator power. Staff remain explicitly enabled and assigned by saved role ID. Metadata and permissions preserve each other and share a concurrency version; assigned roles cannot be deleted. Lost outcomes require authoritative review. Migration `0021_master_permissions` follows `0020_patient_directory`, preserves saved Zone grants and adds no grants or login upgrades. Only approved operators may apply managed migrations. Protected reset, recovery, private files/history, payments and generic domain administration remain excluded. See `docs/zone-role-permissions.md`.

## Release validation

- `pnpm run build` runs `pnpm run validate:release` automatically before typechecking or producing build output. A failed service or browser test blocks the build. The direct artifact `build` command is for compilation only, not release approval.
- The gate runs authentication (including Zone, Courier and role transport), staff CSV/validation, courier, storage-location, role and preference service checks, isolated role/storage-location API/migration/concurrency tests, then the authenticated browser suites including Staff Management, Zone Master, Courier Partner Master, Storage Location Master and role CRUD/recovery in one isolated harness/Playwright invocation. It is registered as the project's `release` validation command. Backend parser/API/migration/race checks run with `pnpm run test:api-foundation`.
- The harness starts Vite in dev mode because the template-preferences spec imports a Vite source module. It does not depend on or alter a managed workflow or its database.
- Master listing notice checks run with `pnpm --filter @workspace/evexia-portal run test:master-listing-notices:browser` and in the default authenticated release harness. They cover desktop/mobile notice absence, retained domain guidance, controls, header-to-panel spacing and actionable export-limit errors; form/import wording remains outside their removal assertions.
- Set `EVEXIA_CHROMIUM_PATH` when a specific supported Chromium executable is needed. Otherwise the gate selects `chromium` / `chromium-browser` from PATH, falling back to Playwright's installed Chromium. Missing or invalid browser executables fail the gate.
- For the download matrix, `EVEXIA_FIREFOX_PATH` and `EVEXIA_WEBKIT_PATH` can select supported Playwright-patched engine executables (WebKit normally uses `pw_run.sh`). Without overrides, Playwright uses its installed engines; on conventional CI install them with `pnpm exec playwright install --with-deps chromium firefox webkit`. Engine versions are printed in test results. WebKit evidence is not native Safari/macOS evidence, and browser download events do not prove user disk completion.
- NixOS development uses `EVEXIA_NIX_DOWNLOAD_ENGINES=1`, `EVEXIA_NIX_BROWSER_LIBRARY_SOURCE` (preinstalled Nix bundle, dependency paths only) and `EVEXIA_NIX_BROWSER_LOADER` (matching current tools' glibc loader). The harness runs `scripts/prepare-nix-download-browsers.mjs` to install missing **current** Firefox/WebKit assets and prepare cached interpreter/library settings without changing browser code or shared-library ABIs. The old preinstalled engines cannot substitute for current ones: launch alone is insufficient to detect protocol incompatibility. Missing dependencies or failed installation fail explicitly.
- Run just the download release gate with `sh scripts/run-authenticated-previews.sh artifacts/evexia-portal/tests/download-logs.preview.spec.mjs`. It covers fail-closed acceptance, committed/lost-ack retry deduplication, server versus browser evidence, cancellation, handoff failures, CSV/XLSX/PDF bytes, and light/dark desktop/mobile Download Logs. Fixtures never use configured account credentials or databases.
- Patient enlarged-text checks run in the default release harness through `playwright.patients.config.mjs`. Run them alone with `sh scripts/run-authenticated-previews.sh artifacts/evexia-portal/tests/patients-layout.preview.spec.mjs`: Chromium/Firefox/WebKit, 390px and 768px, Classic/Modern light/dark, 200% computed text sizes (not device-scale-factor zoom), real CSV/XLSX reviews, form errors/PIN/reference paging, and export dismissal/focus. Only long diagnostics and paged reference/PIN responses are intercepted; login and imports use the isolated API. `EVEXIA_PATIENT_LAYOUT_GREP` and `EVEXIA_PATIENT_LAYOUT_MAX_FAILURES` are diagnostic-only controls; leave both unset for release evidence.
- Roles and Permissions checks run with `sh scripts/run-authenticated-previews.sh artifacts/evexia-portal/tests/roles-permissions.preview.spec.mjs`: existing Chromium CRUD/recovery plus the focused `playwright.roles-permissions.config.mjs` matrix (Chromium/Firefox/WebKit). The matrix covers five-action rows at 1024px/1440px, neutral theme surfaces, separate saved/selected states, catalogue help via hover/keyboard/Escape/touch without drafts (including busy/read-only help), roving keyboard tabs, native mixed groups, search-independent selection/persistence, and both tabs at 200% computed text sizes, 1440px/1024px/375px, Classic/Modern light/dark. Sequential projects use the private authenticated fixture, unique disposable roles and separate results; missing engines fail. Engine/version attachments and screenshots are evidence, not native Safari/macOS verification. Use the same engine overrides/Nix setup as the download matrix.
- `EVEXIA_ROLES_LAYOUT_ONLY=1` and `EVEXIA_ROLES_LAYOUT_GREP` are diagnostic-only controls for that focused spec; leave both unset for release evidence. The former skips the unchanged Chromium baseline, and the latter filters only the tagged cross-engine matrix.
- Outside Replit, run `EVEXIA_CHROMIUM_PATH=/path/to/chromium pnpm run build` (omit the executable override when using installed Playwright Chromium).
- The existing Canvas build also requires `PORT` and `BASE_PATH`; for a full workspace build from a plain shell, supply them (for example `PORT=5173 BASE_PATH=/ pnpm run build`).
- Tests create a fresh, non-persistent browser context for each case; only the two test tabs share storage. Do not replace this with a real browser profile or saved user storage.
