# EVEXIA — Secure Logout & Session Termination

## Context

The following authentication/session foundations have already been implemented or established:

- Super Admin authentication
- MR authentication foundation
- authenticated session creation
- session persistence
- access-token lifecycle
- refresh-token lifecycle
- refresh-token hashing
- refresh-token rotation
- refresh-token reuse detection
- session state/expiry
- session/token security activity

This prompt is specifically for **Logout and secure session termination**.

Do **not** redesign authentication or session creation.

Do **not** create another logout/authentication system.

Follow all existing EVEXIA Engineering & Security Standards.

---

# 1. Objective

Implement a secure, idempotent logout mechanism that terminates the authenticated user's current session and prevents the terminated session's authentication credentials from being reused.

Logout must work correctly for:

- Super Admin
- MR

There are **NO tenants** in EVEXIA.

The logout implementation must integrate with the session/token architecture already implemented.

---

# 2. First Inspect Existing Session Implementation

Before modifying code, inspect the implementation created by the previous session prompt.

Identify:

- session model
- session repository
- session service
- authentication dependency
- access-token validation
- refresh-token storage
- refresh-token rotation
- refresh-token family/reuse detection
- session status
- token/security version mechanism
- refresh cookie configuration
- security/session event implementation
- existing API error handling
- existing tests

Reuse these components.

Do not duplicate:

- session tables
- token tables
- authentication dependencies
- refresh-token logic
- security event systems

If the existing architecture already contains logout/revocation primitives, extend them rather than creating parallel implementations.

---

# 3. Logout Semantics

Define logout as:

> Terminate the authenticated user's current session and invalidate the credentials associated with that session according to the existing token architecture.

Logout must terminate the server-side session.

Do not treat simply deleting a browser cookie as sufficient logout.

The backend must perform the authoritative session termination.

---

# 4. Authentication Requirement

The logout endpoint must be protected appropriately.

The backend must determine the authenticated identity from the validated authentication context.

Do not accept:

```text
user_id
mr_id
email
session_id
```

from the client as the authority for deciding whose session should be logged out.

The server must derive the current identity/session from the authenticated request.

---

# 5. Current Session Identification

Logout should terminate the **current authenticated session**.

Use the session information already established by the authentication/session architecture.

Do not allow a normal logout request to terminate an arbitrary user's session by supplying another user's session ID.

Example attack:

```text
MR A
   ↓
authenticated
   ↓
attempts logout(session_id_of_MR_B)
```

This must not terminate MR B's session.

The backend must enforce session ownership.

---

# 6. Session Revocation

On successful logout:

1. Identify the authenticated identity.
2. Identify the current session.
3. Verify that the session belongs to the authenticated identity.
4. Mark the session as revoked/terminated using the existing session-state mechanism.
5. Invalidate the associated refresh-token/session chain according to the existing token architecture.
6. Prevent further refresh using that session.
7. Clear the browser refresh-token cookie where applicable.
8. Record a logout/security event.
9. Return a safe success response.

Use the existing transaction boundary.

The session state change and associated refresh-token invalidation should be atomic wherever the existing schema permits.

---

# 7. Refresh Token After Logout

After logout, the refresh token associated with the terminated session must no longer be usable.

A request such as:

```text
refresh(previous_refresh_token)
```

after logout must be rejected.

It must not create a new access token.

It must not silently create a new session.

It must not resurrect the terminated session.

The backend must enforce this server-side.

---

# 8. Access Token After Logout

Evaluate the existing access-token architecture carefully.

If access tokens are self-contained JWTs and are intentionally short-lived, do **not** introduce an unnecessary per-token database lookup solely to make every existing access token immediately invalid.

Instead, use the existing security/session mechanism appropriately.

The important requirement is:

- refresh must be impossible after logout
- the terminated session must not be resurrected
- access-token behavior must remain consistent with the existing architecture

If the existing implementation has a session/version/revocation mechanism that supports immediate access-token invalidation, use it.

Do not create a second token-revocation architecture without a clear security requirement.

Document the resulting access-token behavior.

---

# 9. Refresh Cookie

If the existing browser authentication mechanism uses an HttpOnly refresh-token cookie:

On successful logout:

- expire the refresh-token cookie
- use the same cookie name
- use compatible path/domain attributes
- preserve Secure
- preserve HttpOnly
- preserve the established SameSite policy
- preserve `__Host-` protections where already used

Do not expose the refresh token to JavaScript.

Do not store the token in localStorage or sessionStorage.

---

# 10. Logout Idempotency

Logout should be safely idempotent.

If the user attempts logout when:

- the session is already revoked
- the session has already expired
- the refresh cookie is already absent
- the session has already been terminated

the endpoint should not produce an unnecessary error merely because logout has already happened.

The exact HTTP response should follow the project's established API conventions.

Do not reveal sensitive information about whether another session exists.

---

# 11. Logout With Expired Access Token

Handle the case where:

- access token is expired
- refresh token still exists

The logout design must not accidentally allow an expired access token to be used to perform privileged operations.

At the same time, consider how the browser can safely terminate its refresh session.

Use the existing authentication architecture and document the chosen behavior.

Do not weaken authentication merely to make logout convenient.

---

# 12. Logout Event

Record a security/session event for logout.

The event should contain appropriate safe metadata such as:

- event type
- timestamp
- authenticated identity
- session ID
- outcome
- request/correlation ID
- safe client/security metadata if already collected

Do not record:

- password
- access token
- refresh token
- Authorization header
- cookie contents
- refresh-token hash
- cryptographic secrets

Use the existing session/security event mechanism.

Do not create a second event/logging system.

---

# 13. Logout Failure Events

If the system detects a meaningful security-related logout failure, record the appropriate event using the existing security event framework.

Examples:

- unauthenticated logout attempt where relevant
- invalid session state
- session ownership mismatch
- unexpected token/session state

Do not flood logs with harmless repeated logout requests.

Do not log secrets.

---

# 14. API Design

Use the established `/api/v1` convention.

Use an explicit HTTP method appropriate for the existing API architecture.

Prefer a narrowly scoped endpoint such as:

```text
POST /api/v1/auth/logout
```

if that matches the existing authentication route structure.

Do not create multiple logout endpoints for the same operation.

Do not require the frontend to submit the session ID if the backend can derive the current session from the authenticated context.

---

# 15. Request Body

Prefer an empty request body if the current session can be identified from the authentication context.

Do not require unnecessary client-supplied security identifiers.

If the existing authentication architecture requires a specific request field, reuse it only if it is justified and properly authorized.

Do not accept arbitrary user/session identifiers as authority.

---

# 16. Response

Return the project's standard success response.

Do not return:

- access token
- refresh token
- token hash
- session secret
- internal security state

The response should communicate that the logout operation has completed without exposing unnecessary implementation details.

Clear the browser refresh cookie as part of the response where applicable.

---

# 17. Authorization and IDOR Protection

Explicitly test for broken object-level authorization.

The logout operation must never allow:

```text
MR A → logout MR B's session
```

or:

```text
MR A → revoke Super Admin's session
```

through parameter manipulation.

A user must not be able to substitute:

- another session ID
- another user ID
- another MR ID
- another identity identifier

to terminate another identity's session.

Super Admin's system-level privileges must not accidentally bypass ownership requirements when operating through the normal self-logout endpoint.

---

# 18. Super Admin

Super Admin logout must use the same secure session termination mechanism.

Do not create:

- special Super Admin logout token
- special Super Admin cookie
- separate logout endpoint
- separate revocation database
- bypass authentication logic

Super Admin remains a system-level identity, but its session lifecycle should remain consistent with the established authentication architecture.

---

# 19. Transaction and Concurrency Requirements

Logout is security-sensitive.

Use an explicit transaction boundary.

Handle concurrent cases such as:

### Case A

```text
Request 1: logout
Request 2: refresh
```

arriving at nearly the same time.

The implementation must not allow a refresh request to resurrect a session that has already been terminated.

### Case B

Two logout requests arrive simultaneously.

Both should safely result in a terminated session.

### Case C

Logout occurs while a refresh-token rotation is in progress.

Ensure the final state cannot accidentally leave a valid refresh token attached to a terminated session.

Use appropriate locking/atomic state transitions according to the existing database architecture.

Do not rely only on application timing.

---

# 20. Database Rules

Use the existing SQLAlchemy/Alembic architecture.

If schema changes are required:

- create an Alembic migration
- add appropriate indexes/constraints
- preserve foreign keys
- preserve existing session/token relationships
- avoid storing new secrets

Repositories must not independently commit transactions.

Services should own the business operation and transaction boundary according to EVEXIA standards.

---

# 21. Error Handling

Use the existing machine-readable API error system.

Do not leak unnecessary authentication details.

Examples of applicable existing errors may include:

- `AUTHENTICATION_REQUIRED`
- `SESSION_NOT_FOUND`
- `SESSION_REVOKED`
- `SESSION_EXPIRED`

Reuse existing project error codes if they already exist.

Do not create duplicate error systems.

---

# 22. Security Requirements

Verify that logout does not introduce:

- IDOR
- session fixation
- session resurrection
- refresh-token replay
- refresh-token reuse
- privilege escalation
- CSRF vulnerability
- cookie security regression
- token leakage
- sensitive logging
- race-condition vulnerabilities

Preserve:

- HTTPS/secure transport assumptions
- secure cookie attributes
- HttpOnly
- SameSite policy
- Origin/CSRF protections
- existing CORS restrictions
- token rotation
- token reuse detection

Do not weaken an existing security control to make logout easier.

---

# 23. Frontend Integration

Inspect the existing Admin UI authentication flow.

Make the smallest integration necessary for the existing UI to call the new logout endpoint.

Do not redesign the UI.

Do not implement unrelated navigation changes.

After successful logout, the frontend should:

- clear any client-side access-token state that is legitimately held there
- stop treating the user as authenticated
- redirect to the existing login screen according to the current application flow
- not retain sensitive authentication state unnecessarily

The backend remains the security authority.

Do not rely on frontend logout state for security.

---

# 24. Tests

Add comprehensive automated tests.

## Basic logout

- authenticated user can logout
- current session becomes revoked/terminated
- refresh token becomes unusable
- refresh cookie is cleared
- logout event is recorded

## Idempotency

- repeated logout does not cause inconsistent state
- logout of an already-revoked session is safely handled
- logout after session expiry is safely handled

## Authorization

- MR cannot logout another MR's session
- session ID substitution fails
- user ID substitution fails
- Super Admin session cannot be terminated through another user's context

## Refresh-token security

After logout:

- old refresh token rejected
- no new access token issued
- session cannot be resurrected
- refresh-token rotation cannot revive the terminated session

## Concurrency

Test:

- logout vs refresh race
- logout vs refresh rotation
- concurrent logout requests

Verify that no valid refresh credential survives incorrectly.

## Cookie security

Verify:

- cookie is cleared correctly
- HttpOnly remains configured
- Secure remains configured where appropriate
- SameSite remains correct
- `__Host-` behavior remains correct where applicable

## Logging

Verify that logout logs do not contain:

- password
- access token
- refresh token
- Authorization header
- cookie contents
- token hashes
- secrets

## Authentication

Test:

- unauthenticated request
- expired access token
- malformed access token
- invalid authentication context

according to the existing authentication design.

---

# 25. VAPT-Oriented Verification

Manually reason through and, where appropriate, test these attack scenarios:

### IDOR

```text
MR A → attempts to terminate Session B
```

Must fail.

### Session resurrection

```text
logout
↓
reuse refresh token
```

Must fail.

### Refresh race

```text
logout
+
refresh
```

Must not produce a valid session after termination.

### Token replay

```text
logout
↓
reuse previously issued refresh token
```

Must fail.

### Cookie manipulation

Attempt malformed/missing/altered refresh cookies.

Must not bypass authentication.

### CSRF

Attempt cross-origin logout according to the application's browser threat model.

Existing CSRF/Origin protections must remain effective.

### Privilege boundary

Attempt to terminate a Super Admin session from an MR context.

Must fail.

# 27. Definition of Done

The feature is complete only when:

1. Existing authentication/session architecture is reused.
2. Logout terminates the current server-side session.
3. Refresh credentials associated with the session are invalidated.
4. Refresh after logout is rejected.
5. Session resurrection is impossible.
6. Logout is safely idempotent.
7. Session ownership is enforced.
8. IDOR/session-substitution attacks fail.
9. Concurrent logout/refresh behavior is safe.
10. Refresh cookies are securely cleared.
11. Existing cookie security is preserved.
12. Logout activity is recorded using the existing event system.
13. No authentication secrets are logged.
14. Super Admin and MR logout use the established session architecture.
15. No tenant architecture is introduced.
16. Database changes, if any, have proper migrations.
17. Automated security tests pass.
18. Existing authentication tests still pass.
19. Lint/type/static checks pass according to the project tooling.
20. Any unresolved security/design issue is explicitly documented.
