# EVEXIA — Session Initiation, Session Creation & Token Activity

## Context

The Super Admin login/authentication prompt has already been provided and implemented/planned separately.

**Do not redesign or duplicate the login/authentication system.**

This prompt is specifically for the **session lifecycle that begins after a successful login** and for the secure tracking of authentication/session/token activity.

Follow the existing EVEXIA Engineering & Security Standards already established in this project.

### Domain rules

There are **NO tenants** in EVEXIA.

The relevant identity/domain model is:

- **Super Admin** — system-level authority.
- **MR** — authenticated application user.
- **Patient** — patient record accessed according to the application's MR ↔ Patient authorization relationship.

Do not introduce `tenant_id`, tenant middleware, tenant repositories, tenant isolation, or any other multi-tenant abstraction.

---

# 1. Objective

Implement the backend foundation for:

1. Session initiation after successful authentication.
2. Secure session creation and persistence.
3. Access-token lifecycle tracking where appropriate.
4. Refresh-token lifecycle tracking.
5. Refresh-token rotation.
6. Session expiry and revocation state.
7. Session/token security metadata.
8. Authentication/session activity events.
9. Secure session lookup for the currently authenticated user.
10. Protection against token/session reuse and replay.
11. Tests covering the complete lifecycle.

This is **not** the Logout feature.

Logout will be implemented separately after this work is complete.

Do not add a separate logout implementation unless required internally to support session revocation primitives.

Before changing code, inspect the repository and identify the implementation created by the previous Super Admin login prompt.

Specifically inspect:

- existing authentication routes
- authentication service
- JWT/token utilities
- user/MR identity models
- Super Admin identity model or system-role representation
- existing refresh-token implementation
- token-version/security-version mechanisms
- existing session-related tables/models, if any
- database migrations
- settings/configuration
- password hashing
- existing authentication dependencies
- existing authorization dependencies
- existing audit/security logging
- existing tests
- existing Admin UI authentication flow

Reuse the existing implementation wherever it already satisfies these requirements.

**Do not create duplicate authentication, user, role, token, or session systems.**

If a session/refresh-token implementation already exists, extend or harden it rather than replacing it unnecessarily.

---

# 3. Define the Session Model Clearly

A successful login should result in a server-recognizable authenticated session.

Create or use an appropriate persistent session representation.

A session should have a stable opaque identifier such as:

`session_id`

The session record should be associated with the authenticated identity.

Depending on the existing identity model, this may be:

- Super Admin
- MR

Do not create a second identity system merely for sessions.

The session should contain security-relevant lifecycle information such as:

- session ID
- user/identity ID
- creation timestamp
- last-seen / last-refresh timestamp where appropriate
- expiration timestamp
- revoked timestamp, if revoked
- session status
- token/security version where applicable
- safe device/client metadata if collected
- safe IP metadata if collected
- user-agent metadata if collected
- creation/login event reference if appropriate

Do not store:

- raw passwords
- raw access tokens
- raw refresh tokens
- JWT secrets
- encryption keys
- credentials
- unnecessary sensitive browser data

---

# 4. Session ID Requirements

Session identifiers must be:

- opaque
- unpredictable
- non-sequential
- generated using a cryptographically secure mechanism
- safe to expose only where necessary

Never use:

- email address
- MR ID directly
- database sequential ID
- patient ID
- timestamp
- username
- predictable UUID generation

as the session security secret.

A session ID is an identifier, not an authorization mechanism.

Authorization must still be performed using the authenticated identity and existing authorization rules.

---

# 5. Access Token

Use the existing access-token implementation established by the authentication system.

Do not create a second JWT format unless the existing implementation is demonstrably insufficient.

The access token should have appropriate claims such as:

- subject / authenticated identity
- issuer
- audience
- issued-at
- expiration
- token identifier (`jti`) if used by the existing design
- authentication/session reference where appropriate
- required security/version claims already established

Validate:

- signature
- algorithm
- issuer
- audience
- expiry
- required claims
- token/security version where applicable

Do not place sensitive business data inside the JWT.

Do not place:

- passwords
- patient data
- refresh tokens
- secrets
- unnecessary PII

inside the access token.

---

# 6. Access Token Lifetime

Use the existing configured access-token lifetime if already defined.

Do not hardcode a new lifetime inside route/service code.

If the current implementation does not have a properly centralized configuration value, move the value into validated application settings.

The configuration must be:

- server-side
- environment-aware
- validated at startup
- free from hardcoded production secrets

Do not allow the frontend to determine token lifetime.

---

# 7. Refresh Token

The refresh token is a high-value credential.

It must:

- be cryptographically random
- have sufficient entropy
- never be stored in plaintext in the database
- be stored only as a secure cryptographic hash/digest
- have an expiry
- belong to exactly one session
- be rotatable
- be revocable
- be invalid after appropriate reuse detection

The raw refresh token must only exist where required for the authentication exchange.

Never log the raw refresh token.

Never return the raw refresh token in API responses other than the intended secure authentication mechanism.

---

# 8. Refresh Token Rotation

Implement or preserve refresh-token rotation.

When a refresh operation occurs:

1. Validate the presented refresh token.
2. Locate its stored hash/digest.
3. Confirm that the associated session is valid.
4. Confirm that the token has not expired.
5. Confirm that it has not already been consumed/revoked.
6. Issue a new access token.
7. Issue a new refresh token.
8. Persist only the new refresh-token hash/digest.
9. Mark the previous refresh token as consumed/replaced.
10. Maintain the session association.
11. Record the appropriate security event.

The previous refresh token must not remain usable after successful rotation.

---

# 9. Refresh Token Reuse Detection

Treat refresh-token reuse as a security event.

If a previously consumed/revoked refresh token is presented again:

- reject the request
- do not issue a new authenticated session
- do not silently accept the token
- record a security event
- apply the existing refresh-token reuse response/security policy
- revoke the affected session/token family when required by the existing authentication design

Do not reveal unnecessary internal security details to the caller.

Return a safe machine-readable authentication error.

---

# 10. Token Activity

Create a secure representation of important token activity.

At minimum, the system should be capable of recording events such as:

### Authentication

- login success
- login failure
- authentication rejection

### Session

- session created
- session refreshed
- session expired
- session revoked
- session security state changed

### Refresh token

- refresh successful
- refresh rejected
- refresh token rotated
- refresh token reuse detected
- refresh token revoked

### Security

- token validation failure
- security-version/token-version rejection
- suspicious/replayed token event where detected

Do not log raw tokens.

Do not log Authorization headers.

Do not log passwords.

Do not log cookies containing credentials.

---

# 11. Session Activity vs Audit/Event Logs

Keep the concepts separate.

### Session record

Represents the **current lifecycle/state of a session**.

Example:

- active
- expired
- revoked

### Security/session event

Represents an **event that happened to or because of a session**.

Example:

- login succeeded
- refresh occurred
- refresh token rotated
- token reuse detected

Do not turn the session table into an unbounded event log.

Do not turn the event log into the source of truth for current session state unless the architecture explicitly requires event sourcing.

For this project, prefer a clear session state model plus append-oriented security/session events.

---

# 12. Session Status

Use an explicit state model rather than scattered boolean flags.

Possible states should be evaluated against the existing implementation, for example:

- ACTIVE
- EXPIRED
- REVOKED

Do not introduce unnecessary states.

The server must determine the effective state based on:

- explicit revocation
- expiration
- security/token-version invalidation
- refresh-token state
- other existing authentication security rules

The frontend must never be authoritative for session state.

---

# 13. Current Session Information

Add the backend foundation required for an authenticated user to retrieve information about their own current session.

The endpoint must:

- require authentication
- identify the authenticated user from the validated authentication context
- resolve the session server-side
- return only safe session metadata
- never return credentials or token secrets

Example safe response fields may include:

- session ID
- status
- created at
- last activity/refresh
- expires at
- device/client metadata if collected
- approximate/security metadata only where justified

Do not expose:

- refresh-token hash
- access token
- raw token identifiers where unnecessary
- password data
- secret configuration
- internal security implementation details

---

# 14. Active Sessions

If the existing architecture supports multiple concurrent sessions, provide the backend foundation to identify sessions belonging to the authenticated user.

Authorization must ensure:

**MR A cannot inspect MR B's sessions.**

Similarly:

**A Super Admin session cannot accidentally be treated as an MR session.**

Do not introduce patient-level session ownership.

Patients are domain records, not authenticated users unless the existing product explicitly establishes a patient authentication model.

Do not invent patient login.

---

# 15. Super Admin Session Rules

The Super Admin is a system-level identity.

Its session must follow the same secure authentication/session mechanics as other authenticated identities while preserving the special system-level authorization rules established by the Super Admin implementation.

Do not create a separate token system for Super Admin.

Do not create a separate JWT implementation for Super Admin.

Do not bypass normal session validation because the identity is Super Admin.

Do not allow normal user APIs to:

- downgrade Super Admin
- disable Super Admin
- delete Super Admin
- alter Super Admin security state

unless explicitly designed and authorized as part of the system-level security model.

---

# 16. Cookies and Browser Security

If the existing authentication design uses an HttpOnly refresh-token cookie, preserve that design.

The refresh cookie should use the appropriate secure attributes, including:

- HttpOnly
- Secure in production
- appropriate SameSite policy
- appropriate path
- existing `__Host-` prefix protections where already established

Do not move refresh tokens into:

- localStorage
- sessionStorage
- browser IndexedDB
- ordinary JavaScript-accessible cookies

Do not expose refresh tokens to frontend JavaScript.

The access token should follow the existing authentication architecture.

Do not invent a second browser storage strategy.

---

# 17. CSRF / Origin Protections

Preserve the existing authentication CSRF/origin protections.

For browser-based refresh operations:

- validate the expected Origin/CSRF protection mechanism where applicable
- preserve existing explicit CORS configuration
- do not use wildcard origins for authenticated credentialed requests
- do not weaken existing production protections

Do not disable these protections merely to make the frontend integration easier.

---

# 18. Concurrency Requirements

Session/token rotation is security-sensitive and must be safe under concurrent requests.

Handle cases such as:

- two refresh requests arriving simultaneously
- the same refresh token being presented concurrently
- refresh immediately followed by another refresh
- session expiry occurring during refresh
- revocation occurring during refresh

Use appropriate database transaction boundaries and locking/atomic state transitions.

Do not rely on application-level timing assumptions.

A consumed refresh token must not be successfully consumed twice because of a race condition.

Add tests specifically for concurrent refresh/reuse behavior.

---

# 19. Database Requirements

Use the existing SQLAlchemy/Alembic architecture.

If a new session/token table is required:

- create a proper Alembic migration
- use foreign keys where appropriate
- add appropriate indexes
- add uniqueness constraints where required
- add timestamps consistently
- avoid storing raw secrets
- avoid unnecessary PII
- use explicit transaction boundaries

Repositories should perform persistence operations.

Repositories should not independently commit transactions.

Services should own business operations and transaction boundaries according to the established EVEXIA architecture.

---

# 20. Data Retention

Do not retain session/security information indefinitely without a reason.

Define retention behavior for:

- expired sessions
- revoked sessions
- consumed refresh tokens
- security/session events

The retention period must be configuration-driven where operationally appropriate.

Do not implement destructive cleanup in a way that could remove required security/audit evidence prematurely.

If the project does not yet have a finalized retention policy, implement the schema and lifecycle safely without inventing an arbitrary compliance retention period. Document the unresolved retention decision.

---

# 21. Logging

Application logs must never contain:

- passwords
- access tokens
- refresh tokens
- Authorization headers
- cookie contents
- token hashes/digests
- encryption keys

Use structured logs.

Include safe identifiers such as:

- request ID
- correlation ID
- session ID where appropriate
- authenticated identity ID where appropriate
- event type
- outcome

Avoid logging unnecessary PII.

---

# 22. Authorization

All session APIs must be protected server-side.

Never rely on:

- frontend route protection
- hidden UI elements
- localStorage
- URL obscurity
- session ID secrecy

as authorization.

The backend must determine:

- who is authenticated
- which session belongs to that identity
- whether the requested operation is permitted

An authenticated MR must not be able to manipulate or inspect another MR's session by changing an ID.

An authenticated user must not be able to substitute another session ID into a request and gain access.

---

# 23. API Contract

Follow the existing `/api/v1` API convention.

Use:

- explicit HTTP methods
- explicit request/response Pydantic models
- response models
- bounded outputs
- machine-readable error codes
- safe error messages
- request/correlation IDs

Do not expose ORM objects directly.

Do not return internal database fields.

Do not create broad generic session endpoints when a narrowly scoped endpoint is sufficient.
