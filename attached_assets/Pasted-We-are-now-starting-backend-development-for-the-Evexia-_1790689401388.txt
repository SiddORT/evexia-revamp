We are now starting backend development for the Evexia platform.

IMPORTANT CONTEXT:

The existing Replit project currently contains ONLY a mock/prototype React UI for:

1. Login
2. Masters / master-data related screens

The frontend is currently a UI prototype. Do not assume that the rest of the Evexia product has already been implemented.

We now need to establish a secure, scalable, production-oriented backend foundation before building business functionality.

Backend technology:

* Python
* FastAPI
* PostgreSQL
* SQLAlchemy 2.x
* Alembic
* Pydantic v2
* JWT authentication
* Secure password hashing
* REST APIs
* React frontend remains unchanged unless integration requires a minimal change

==================================================

1. CORE ARCHITECTURE PRINCIPLES
   ==================================================

Build the backend as a modular monolith.

Do NOT create microservices at this stage.

The architecture must allow individual modules/services to be separated later if the product grows.

Use clear separation between:

* API/routes
* schemas
* business/service layer
* database/models
* repositories/data-access where appropriate
* integrations/helpers
* configuration
* security
* storage
* auditing
* background jobs/tasks if required

Business logic must NOT be placed directly inside FastAPI route handlers.

Routes should be thin and call service-layer functions.

Do not tightly couple business logic to external providers.

==================================================
2. SECURITY / VAPT-FIRST APPROACH
=================================

The backend must be designed with OWASP ASVS / OWASP API Security principles in mind.

Treat security as a first-class requirement, not something to add later.

Implement the foundation for:

* secure authentication
* authorization
* role-based access control
* least privilege
* input validation
* output validation
* parameterized database queries
* secure password hashing
* JWT security
* token expiration
* secure configuration
* secrets through environment variables
* rate limiting architecture
* audit logging
* security event logging
* safe error handling
* prevention of information leakage
* CORS configuration
* security headers where applicable
* request ID / correlation ID
* API versioning
* protection against common API abuse
* file upload validation
* MIME/type validation
* file size limits
* path traversal protection
* SSRF protection where URLs are accepted
* prevention of mass assignment
* IDOR protection through authorization checks
* SQL injection protection
* XSS-safe handling
* CSRF considerations where applicable
* brute-force protection for authentication
* account enumeration protection
* secure password reset architecture
* session/token revocation strategy

Do NOT expose stack traces, SQL errors, internal paths, secrets, tokens, or sensitive implementation details in API responses.

Production error responses must be generic and safe.

Detailed errors should go only to secure server-side logs.

Do not log:

* passwords
* access tokens
* refresh tokens
* OTPs
* API keys
* secrets
* authorization headers
* sensitive personal information unless explicitly required and appropriately protected

==================================================
3. AUTHENTICATION
=================

Create a proper authentication foundation.

Prepare support for:

* user registration
* login
* logout
* access tokens
* refresh tokens if required by the architecture
* current-user endpoint
* password hashing
* password change
* password reset architecture
* account lock/rate limiting strategy
* role-based authorization

Use a strong password hashing algorithm such as Argon2id if supported by the environment.

Never store plaintext passwords.

Never return password hashes through APIs.

JWT configuration must come entirely from environment/configuration.

Never hard-code JWT secrets.

Use short-lived access tokens.

Design refresh-token handling securely rather than storing long-lived access tokens in the browser.

Review the existing React login UI and adapt the API contract to it rather than redesigning the UI.

==================================================
4. DATABASE
===========

Use PostgreSQL.

Use SQLAlchemy 2.x.

Use Alembic for migrations.

Never modify production database schema manually as the normal workflow.

All schema changes must be represented through Alembic migrations.

Use UTC timestamps consistently.

Prefer UUID identifiers for externally exposed entity IDs where appropriate.

Do not expose sequential database IDs unnecessarily.

Establish common model conventions for:

* id
* created_at
* updated_at
* created_by where appropriate
* updated_by where appropriate
* status
* soft deletion where appropriate

Do NOT blindly add soft deletion to every table.

Use it only where business requirements justify it.

Add appropriate database indexes and uniqueness constraints.

Do not create unnecessary tables.

==================================================
5. MULTI-TENANCY / ORGANIZATION READINESS
=========================================

The system should be designed with future organization/tenant isolation in mind.

Do not assume that all users belong to one global organization.

Analyze the existing UI and establish whether Evexia should have:

* organizations/tenants
* users
* roles
* permissions
* user-organization membership

If these are appropriate, design the foundation so tenant isolation can be enforced consistently.

A user must never be able to access another tenant's data merely by changing an ID in an API request.

Authorization must happen at the service/data-access level, not only in the frontend.

==================================================
6. FILES AND MEDIA — VERY IMPORTANT
===================================

DO NOT USE:

* Replit Blob Storage
* local filesystem as persistent application storage
* arbitrary files stored inside the application repository
* database BLOB storage for normal uploaded files/media

All files and media must be designed around an S3-compatible object-storage architecture.

However, DO NOT hard-code business logic directly to AWS S3 SDK calls throughout the application.

Create a storage abstraction/service.

For example:

StorageService
upload()
download()
delete()
exists()
generate_presigned_upload_url()
generate_presigned_download_url()
get_object_metadata()

The business layer should call StorageService rather than boto3/S3 directly.

The implementation should be replaceable.

The system must be designed so that in the future we can configure:

AWS S3
or another S3-compatible object store

without rewriting business logic.

DO NOT create actual persistent local file storage as a fallback.

If local development requires a storage emulator, keep it clearly separated from production configuration.

==================================================
7. S3 OBJECT KEY STRUCTURE
==========================

Define a standardized object-key convention now.

Do NOT treat S3 as a random flat bucket.

Use a predictable hierarchy such as:

{environment}/{tenant_id}/{module}/{entity_type}/{entity_id}/{category}/{uuid}-{safe_filename}

Example:

production/
tenant-uuid/
users/
user-uuid/
documents/
uuid-document.pdf

or:

production/
tenant-uuid/
patients/
patient-uuid/
reports/
uuid-report.pdf

The exact structure should be finalized based on the Evexia domain model.

Important:

* Never trust the original filename as the storage path.
* Sanitize filenames.
* Generate unique object identifiers.
* Prevent path traversal.
* Do not expose bucket credentials to the frontend.
* Prefer pre-signed URLs for direct uploads/downloads where appropriate.
* Validate file type and size before accepting uploads.
* Store metadata in PostgreSQL, not the actual binary content.
* Keep object keys separate from user-provided filenames.
* Never allow a user to arbitrarily specify an S3 object key.

Create a file/media metadata model if appropriate containing fields such as:

* id
* tenant_id
* original_filename
* object_key
* content_type
* size
* checksum where appropriate
* entity_type
* entity_id
* category
* uploaded_by
* created_at
* status

Do not expose internal bucket credentials.

9. TEMPLATE-DRIVEN COMMUNICATION
================================

All email/SMS/WhatsApp notifications must eventually support templates.

Do not hard-code message text inside business logic.

The architecture should support:

* template code
* template name
* channel
* sender configuration
* recipient
* subject where applicable
* body/content
* variables
* language
* provider
* provider-specific configuration
* active/inactive status
* versioning if required

Example conceptual usage:

notification_service.send(
template="USER_WELCOME",
channel="EMAIL",
recipient=user.email,
variables={...}
)

The service should resolve:

* template
* sender
* provider
* credentials/configuration
* channel-specific formatting

based on centralized configuration.

Do not put provider credentials in source code.

All credentials must come from environment variables or secure secret management.

13. API DESIGN
==============

Use API versioning.

For example:

/api/v1/auth/...
/api/v1/users/...
/api/v1/masters/...

Create consistent response and error patterns.

Use appropriate HTTP status codes.

Validate all request bodies using Pydantic.

Do not trust frontend validation.

Backend validation is authoritative.

Implement pagination for list APIs where appropriate.

Avoid returning unrestricted large datasets.

==================================================

for production.

Do not allow credentials with wildcard origins.

Create separate development and production configuration.
